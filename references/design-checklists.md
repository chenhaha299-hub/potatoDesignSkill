# 可用性设计检查清单

走查界面时逐项打勾。任何一项不过，就是一个明确的"用户会卡住"的地方。

## A. 可发现性（用户能找到吗）

- [ ] 核心任务的操作按钮在首屏可见，且是文字按钮（不是只有图标）
- [ ] 用户第一次打开，3 秒内能说出"这产品是干嘛的"
- [ ] 页面有明确的"我现在在哪"指示（导航高亮/标题/面包屑）
- [ ] 修改信息、查历史、联系客服等常见需求有入口（不藏进汉堡菜单）
- [ ] 功能不用"悬浮手势/长按/三指"等隐藏操作触发
- [ ] 删除/编辑等常用功能**常显**，不靠 hover 才显示（实战教训：删除按钮 opacity:0 只有悬停出现，用户反馈"没地方删除"——hover 隐藏 = 用户找不到 = 功能不存在）
- [ ] 层级/嵌套页面有**颜色区分**（同布局不同层级时，用色系区分避免混淆，如一级绿/二级橙/三级紫）

## B. 反馈（用户知道发生什么了吗）

- [ ] 点击任何可点元素有即时视觉反馈（≤ 100ms）
- [ ] 提交/保存后有明确结果提示（成功/失败/排队）
- [ ] 等待 > 1 秒时有加载提示（骨架屏/进度条/spinner）
- [ ] 操作成功后有下一步引导（"预约成功，去看看"）

## C. 认知负荷（用户需要多想吗）

- [ ] 一屏只有一个主要任务
- [ ] 表单字段 ≤ 7 个/屏（超过就分步）
- [ ] 有默认值/智能默认（日期默认今天、城市默认定位）
- [ ] 术语是用户的话（"订座"不是"库存预定"）
- [ ] 没有同时展示 5 个以上并列选项且无主次

## D. 容错（用户出错会怎样）

- [ ] 输入即时校验（填完即验，不是提交才报错）
- [ ] 错误提示说人话 + 给解法（"手机号少一位"）
- [ ] 删除/取消/付款等破坏操作有二次确认
- [ ] 有撤销/返回路径（误操作能回来）
- [ ] 表单数据不会因刷新/返回丢失

## E. 移动端（手机场景）

- [ ] 所有可点元素 ≥ 44×44px（Fitts 定律）
- [ ] 核心操作在拇指易达区（下半屏）
- [ ] 适配 iPhone 安全区（刘海/Home 条）与安卓全面屏
- [ ] 一屏不横向滚动；表格在手机上转卡片
- [ ] 输入框调起正确的键盘（数字输入调数字键盘）

## F. 视觉与可访问性

- [ ] 正文对比度 ≥ 4.5:1，大号文字 ≥ 3:1
- [ ] 不用颜色单独传达信息（红=错误的同时有图标/文字）
- [ ] 可点元素有 hover/focus 状态（网页）；键盘可操作（网页）
- [ ] 全站主色 ≤ 5 个，样式统一
- [ ] 字体支持系统放大，放大后不破版

## G. 状态完整性（每个页面都有）

- [ ] 空状态：说明 + 下一步引导 + 按钮
- [ ] 加载状态：骨架屏或 spinner
- [ ] 错误状态：人话 + 重试按钮
- [ ] 成功状态：明确祝贺/确认 + 下一步
- [ ] 断网状态（移动端）：有提示，不白屏

## 摩擦清单输出模板

| 位置 | 用户会卡在哪 | 严重度 | 最小修复 |
|---|---|---|---|
| 预约页 | 时段满了用户不知道，提交才报错 | 高 | 已满时段直接置灰 |
| 首页 | 不知道这是干嘛的 | 中 | 顶部一句话说明 + 主按钮 |


## H. 迭代反馈实战流程（2026-08 教训）

用户对已有界面提修改意见时，按此流程（能少返工 3 轮）：

1. **先确认用户熟悉的产品格式**：用户说"模仿 XX App 那种格式"时，先问"你常用哪个 App，它长什么样"——不要凭想象设计；
2. **截图逐项确认**：用户给标注截图（红框/箭头/打叉），对每个标注列"我看到了 X → 理解为 Y"，一次性确认后再动手；
3. **动词字面执行**："移动按钮"= 搬位置，不要顺带"统一/合并/优化"；
4. **改前先 grep 现状**：确认元素现在有几个、在哪，避免"我以为有两个"；
5. **交互入口显式化**：任何功能要有可见入口，双击/长按等隐藏手势只能作快捷方式，不能是唯一入口（用户明确选择隐藏手势作为唯一入口的情况除外）。
